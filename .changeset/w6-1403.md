CLI's `parseNonEvmEnvelope` (non-EVM `tx_ready` dispatch) now fails closed instead of silently forwarding a non-native token symbol. Previously, when `resolved.labels.token_resolved` differed from the chain's native ticker, the parser set it as the send `symbol` while the amount had already been converted using the chain's *native* decimals — a future non-native token envelope (SPL, TRC-20, etc.) would sign with a magnitude-wrong amount. Phase D only wires native sends today; a non-native `token_resolved` now throws `VaultError(NotImplemented)` instead of guessing.
